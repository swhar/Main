## 1. Canonical Entry Header — Rationale

**Problem.** `/recall` reads four whole memory files plus project files plus `knowledge/`. Without a stable structural anchor, retrieval is full-text scan. As entries accumulate, this gets noisy: blockquote bodies (`> **Date:** ...`) are easy to read but hard to slice into entries via grep, because the only delimiter is a blank line — and blank lines appear inside entries too.

**Design.** A single H2 line per entry: `## [YYYY-MM-DD] TYPE: Title [#tags]`. This:
- Provides a stable per-entry boundary (`grep '^## \['` returns one line per entry).
- Makes date a first-class field for sort / range filter.
- Promotes a short title to a first-class field for index summaries.
- Adds optional tags without forcing them — entries without `[#...]` still match `^## \[YYYY-MM-DD\] TYPE:`.

**Backward compatibility.** Body formats (Decision log, Learning entry, Action item) in `prompts/elite-techniques.md` are unchanged. The header is purely additive. Pre-convention entries (none exist today) keep working — `/recall` falls back to whole-file scan when the header is missing. No command needs to change to keep producing usable entries; commands can opt in to producing the header when convenient.

**Why uppercase TYPE.** Grep contrast against prose. `grep DECISION` is unambiguous; `grep decision` is not.

**Why brackets around the date.** Distinguishes the header date from any date that appears in the title or body. `^## \[2026-` is a sufficient anchor.

**Tag taxonomy.** Starter set covers domain (work/personal/health/finance/relationships), function (strategy/tactics/planning/research/meta), and task status. Project tags reuse the project filename. Free-form additions allowed; pruned in weekly review. Kept lowercase, hyphenated, no spaces — consistent with common tag systems.

## 2. `memory/index.md` — Rationale

**Problem.** `/recall` and `/briefing` both need a fast snapshot of the system's state. Today they have to read every memory file in full just to surface "what's hot." That's fine when files are small — bad as they grow.

**Design.** A derived view with four sections:
- **Active Goals** — pulled from `profile.md`
- **Open Decisions (latest 5)** — sorted by canonical header date
- **Recent Learnings (latest 5)** — same
- **Active Projects** — one line per file in `projects/`

Plus a Quick Links footer.

**Regenerability.** This is the critical property. The index is **derived**, not authoritative. The doc says explicitly: regenerated by `/recall` or `/briefing`, do not hand-edit. This prevents drift between the index and the source files. If a user edits the index, the next regen overwrites it — by design.

**Why latest 5.** Cheap heuristic. The index is meant to be skimmable in 10 seconds. If a user wants more, they `/recall <topic>` or read the source file directly.

**Why this works without command changes today.** `/recall` and `/briefing` already read memory files. Adding "also write a refreshed `index.md`" is a small extension but **not required** for the index to be useful — even un-regenerated, it documents the structure and points to source files via the Quick Links section. The scaffolding ships value before any command is updated.

## 3. Weekly Archive Pattern — Rationale

**Problem.** `tasks.md` → "Completed This Week" grows without bound. Without rotation, it becomes a noisy log nobody reads.

**Design.** ISO-week-numbered rollups in `memory/archive/YYYY-Www.md`. Today (2026-05-07) is W19. Each rollup contains:
- Completed task entries moved out of `tasks.md`
- **Title-only references** to that week's decisions and learnings — bodies stay in their primary files
- A free-form reflection block from `/weekly-review`

**Why title-only for decisions/learnings.** Avoid duplication. Decisions and learnings are long-lived; they belong in their primary log. The weekly file is a *time-window view*, not a duplicate store. This keeps `/recall` from returning two copies of every decision.

**Trigger.** `/weekly-review` (Agent A's territory). Until that command exists, the rollup can be performed manually following the structure in `MEMORY-CONVENTIONS.md` §4.

**Why ISO weeks.** Universally defined, monotonic, sortable as strings. `2026-W19.md` sorts correctly between `2026-W18.md` and `2026-W20.md`. Avoids ambiguity at year boundaries.

**`README.md` over `.gitkeep`.** A `.gitkeep` would satisfy the directory placeholder requirement but teach nothing. A README documents the naming pattern, what belongs there, and what doesn't — solving "where should this go?" the moment someone opens the folder. Trade-off: one extra file to maintain (low — the rules don't change often).

## 4. Quarterly Split — Recommendation: NO

**Recommendation:** Do **not** split `decisions.md` or `learnings.md` per quarter. Use a soft yearly archival rule instead, triggered only when entries exceed a threshold.

**Reasoning:**

**a. The system is empty today.** Both files contain zero entries. Pre-splitting fragments grep targets and forces every command (`/recall` especially) to know where to look. Cost is paid immediately; benefit is hypothetical.

**b. Quarterly cadence is arbitrary.** Decisions and learnings don't naturally cluster by quarter — projects, themes, and life events span multiple quarters. A user looking back at "what did I decide about my career last year" wants one file to scan, not four.

**c. Single-file scan is cheap until it isn't.** Modern grep handles 100K-line files trivially. The pain point is human: scrolling and visual noise. That pain hits well after the file has any meaningful volume — likely 1+ year of active use.

**d. Threshold-based archival adapts to actual usage.** The soft rule (500 entries / 10K lines / >1 year) lets a heavy user archive at month 6 and a light user keep one file for years. Quarterly splits force the same cost on everyone regardless of fit.

**e. Reversibility.** Today's "no split" is trivially reversible — when the file gets painful, archive older entries to `memory/archive/decisions-2025.md` and continue. Today's "yes, split now" is harder to reverse: every command and habit forms around the split, and consolidating later is more work.

**Counter-argument considered.** Quarterly splits would make weekly/monthly review easier ("show me all decisions from Q2"). But the canonical header carries `[YYYY-MM-DD]`, so a date-range grep across one file does the same job — `grep '^## \[2026-0[4-6]' decisions.md` returns Q2. The split adds no capability that the header doesn't already provide.

**Conclusion.** No quarterly file scaffolded. The archive folder exists for the eventual yearly archive; today it is documented but empty.
